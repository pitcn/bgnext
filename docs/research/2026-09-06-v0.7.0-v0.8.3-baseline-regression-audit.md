# BGNext 0.7.0—0.8.3 原版行为回归审计

## 审计口径

- BGNext 版本范围：`v0.7.0`、`v0.8.0`、`v0.8.1`、`v0.8.2`，以及仓库当前公开的 0.8.3 状态 `fb9fff4`。
- 唯一官方上游基准：仓库固定的 BGLite 纯净版 2.4.2（`5649f58`）。
- 原版行为参考：维护者独立保存的 BiaoGe 2.3.5。
- BGLitePlus 2.5.4 和其他作者作品不作为官方版本或正确性基准。
- 比较重点是玩家可观察行为、处理顺序、状态边界和失败模式；本文不保存或复制第三方源码片段。

## 总结

不能把 0.7.0—0.8.3 判断为“只增加功能、没有损坏基础流程”。审计确认了五条已经发生过的回归；本地候选正在逐项修复，但这些修复尚未进入公开 0.8.3。另有高风险差异仍缺少足够的真实集成证据。

最重要的当前结论：

1. 公开 0.8.3 仍不包含“成交后预填账单行的交易欠款匹配”热修；修复仅存在于本地提交 `cdeb5f8`。
2. 表格装备的 `Alt+Ctrl+Shift` 交换操作在 0.7.0—公开 0.8.3 会被新增快捷键提前截获；本地修复已恢复交换和 `Alt+Shift` 的原版优先级。
3. 0.8.3 已修复 0.7.0—0.8.2 中的开拍窗口 nil 调用、价格目录标量崩溃、团长 Alt+左键错误进入心愿单、成交保存受界面失败影响和更新日志裁切。
4. 拍卖发送、成交写账、交易、欠款、邮件和清表已经形成多层包装链。单模块测试通过不能证明完整加载顺序和真实 WoW 事件链安全。

## 与 BiaoGe / BGLite 2.4.2 的高风险处理差异

### 1. 拍卖协议被固定为第一代普通模式

BGNext 自 `abbcb83` 起删除了原版的拍卖代际、模式和重置阈值选择，发送端固定使用第一代 `normal` 消息。接收端仍能识别第一代和第二代消息，因此基础混用通常可工作；但 BGNext 团长无法再发起原版第二代倒计时同步、暂停/恢复相关流程。

这是主动简化，不是本轮新发现的单点崩溃，但它贯穿 0.7.0—0.8.3，并且同一删改曾遗漏 `ClearAllFocus` 而产生生产错误。后续不能再把它标为“与官方完整等价”。

### 2. 拍卖消息增加了发送者和频率校验

原版收到团队拍卖消息后直接按协议处理；BGNext 要求开拍/取消/暂停/恢复消息来自缓存中的团长或拾取职责，出价来自实时团队名单，并限制同一玩家对同一拍品的接收频率。

安全收益明确，但公开 0.8.3 的开拍权限使用延迟刷新约 0.5 秒的名单缓存，而出价使用实时名单。团队刚建立、团长或拾取职责刚变化时，合法的第一条开拍消息存在被静默丢弃的竞态。本地修复已把控制消息也改为消息边界的实时职责快照，并保留缓存兜底；真实游戏事件时序仍需验证。

### 3. `BG.StartAuction` 与 `BG.HookCreateAuction` 被连续包装

当前加载顺序为基础 Auction → 价格运行时 → 队列运行时 → 团长工具。价格和队列先后替换 `BG.StartAuction`；价格、队列和团长工具先后替换 `BG.HookCreateAuction`。

这些包装目前都保存并调用前一层，但它们依赖固定 TOC 顺序。任一较早模块初始化失败，后续保护、价格预填、队列二次确认或异常出价确认都会部分缺失。现有测试大多分别加载单层模拟环境，没有证明四层在完整插件加载图中共同工作。

### 4. 玩家身份只完成了部分规范化

拍卖、交易和账单买家开始保存/比较 `名字-服务器`；但消费、欠款等原版汇总模块仍按界面可见文本分组，而且这些模块与 BGLite 2.4.2 保持相同。

结果是新规范身份与旧短名汇总并存。存在同名跨服玩家时，明细可能保持区分，而消费/欠款汇总发生合并或拆分。单服普通团队通常不触发，跨服或连接服需要专门测试。

### 5. 当前结算和对账改为短期、显式采集

BGNext 为隐私目的不加载官方交易/邮件历史，并把对账改为用户点击开始后才临时采集。这个差异是设计要求，不应恢复成跨团持久历史。

但是公开 0.8.3 在任何 `GROUP_ROSTER_UPDATE` 时都会停止并清空本次临时结果。成员掉线、进出团或队伍变动发生在账单播报期间，会让对账结果消失。本地修复改为只在离团或已绑定的账单发送者离队时清空，无关成员变化继续采集。

### 6. 保存数据缺少真正的迁移和类型修复

`schemaVersion` 一直写为 1，新增数据结构没有逐版迁移。多个根字段仅用 `旧值 or {}` 初始化，不检查旧值类型。已用最小复现确认：`currentSettlement` 或 `currentRaid` 若因旧版本、手改或局部损坏变成数字，初始化/开始团队会直接报 Lua 错误。

正常 0.7.0—0.8.3 保存文件通常会生成表，因此这不是已证明的普通升级必现错误。本地修复已对根数据、当前团、当前结算及其列表进行逐字段类型恢复并补测试；更高版本 schema 迁移仍未建立。

## 测试为何没有提前拦住

- 各发布状态的 Lua 测试都能全绿，但相当一部分断言只搜索源码字符串，没有执行完整基础模块。
- 拍卖、交易、账单和邮件的大文件通常被拆出局部函数或用模拟对象测试，缺少一套按真实 TOC 顺序加载并重放事件的集成夹具。
- 快捷键测试覆盖 Alt、Ctrl、Ctrl+Shift 和 Alt+Ctrl，却没有覆盖 Alt+Shift、Alt+Ctrl+Shift，也没有与原版优先级矩阵做差分测试。
- 发送者校验测试覆盖静态名单和解析边界，没有覆盖团队刚建立或职责刚切换时的延迟刷新。
- UI 测试无法证明 NDUI 等皮肤插件对受保护框体、输入焦点和脚本替换的影响。
