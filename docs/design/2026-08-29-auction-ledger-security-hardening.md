# 拍卖与对账通信安全加固设计

- 日期：2026-08-29
- 状态：已确认，待实现
- 关联：GitHub Issue #3

## 目标

修复当前拍卖协议的消息洪泛与异常数值风险，并让对账功能符合网易 DD 活动关于“不得生成他人的历史信息记录”和用户主动控制的要求。保留正常团队拍卖与当前团对账能力，不新增通信协议，不扩大数据采集范围。

## 拍卖消息

`SendMyMoney` 只接受当前团队成员发送的、格式有效的消息。拍卖编号、物品编号、持续时间和金额必须是有限整数，并处于明确范围内；`NaN`、无穷大、负数、科学计数法产生的越界值和超出游戏金币上限的金额均被静默拒绝。

接收端按“发送者 + 拍卖编号”执行内存限流，同一组合一秒内只处理一条出价。限流状态不写入 SavedVariables，在重载后自然销毁。竞拍欢呼语使用独立的五秒限流，并在发送聊天消息前重复验证团队成员、拍卖编号和金额，避免第二个事件处理器绕过主出价入口的保护。

控制命令继续沿用现有团长或物品分配者授权，不改变正常权限模型。版本响应继续使用现有限流；版本竞态兼容问题不纳入本次安全 PR。

## 当前对账

对账不再后台自动记录广播。玩家必须在对账界面主动点击“开始对账”，插件才会临时识别当前团队中的账单通报。界面应明确说明数据仅用于当前团队会话，重载、退出、离团、团队身份变化、主动停止或对账完成后清空。

临时数据只存在内存，不写入 `BiaoGe` 或 `BiaoGe.BGNext`。只保留完成当前对账所需的装备标识、买家和金额；不保留原始聊天文本、完整团员名单或多份历史账单。插件自己的表格及现有 BGNext 当前团结算数据不受影响。

开始账单的聊天发送者会绑定为本次来源。后续聊天行和 `DuiZhang-` 插件消息必须来自同一规范化角色身份且仍属于当前团队，否则静默丢弃。临时缓存设置固定上限；超过行数、条目数、单条长度或等待时间时终止本次识别并清空，避免恶意或损坏客户端造成无界内存增长。

## 数据与兼容性

本次变更不增加 SavedVariables 字段，不迁移或读取旧的他人账单历史。既有 `BiaoGe.duizhang` 内容不再由 BGNext 对账功能展示或继续写入；本 PR 不主动删除用户磁盘中的旧字段，避免静默销毁数据。发布说明会提示用户可通过清理插件数据删除旧记录。

对账广播仍兼容当前已识别的金团账本、金团表格和大脚可见通报格式，但只有在用户主动开始且来源身份通过验证时才处理。所有新增安全状态均为本地内存对象。

## 测试与验收

测试先失败再实现，覆盖：

1. 拒绝无穷大、非整数、负数和越界拍卖字段；合法边界仍通过。
2. 同一玩家同一拍卖一秒内重复出价只接受一次；不同拍卖互不影响。
3. 欢呼语拥有独立五秒限流，不能被主处理器状态替代或绕过。
4. 未主动开始对账时不采集；开始后只接受绑定发送者和当前团队成员。
5. 对账缓存达到上限时失败关闭；离团、停止和完成后清空。
6. 源码扫描确认运行路径不再向 `BiaoGe.duizhang` 写入他人账单、原始消息或团员名单。
7. 完整 Lua 测试、基线完整性、发布包检查、隐私通信扫描和 `git diff --check` 全部通过。

实机验收需覆盖至少一个实际团队拍卖和一次当前团对账；自动化通过只能标记为代码覆盖，不能替代游戏内验证。
