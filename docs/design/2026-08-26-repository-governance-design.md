# BGNext 仓库治理与专业化文档设计

日期：2026-08-26
状态：已由维护者确认

## 1. 背景与目的

BGNext 发起于对网易 DD 公开举办的「BGLite 增强版开发激励活动」的响应。项目以官方发布的 BGLite 纯净版为技术基线，目标是在不突破游戏规则、平台审核要求、隐私边界和知识产权边界的前提下，建立一个安全、透明、可持续的社区共创维护项目。

项目是独立、非官方的社区项目，不代表网易、暴雪或 BGLite 原作者的官方立场。活动名称只用于说明项目缘起，不构成合作、认证、推荐或商业背书。

当前 Git 基线为 BGLite 2.4.0，共 188 个上游文件。后续治理文档与 GitHub 配置文件不得修改这些基线文件；任何运行时功能改动必须通过独立 Pull Request 提交、审查和测试。

## 2. 首要原则

安全、隐私和合规优先于功能完整度、开发速度、下载量、排名及任何经济激励。

任何功能即使有明显使用价值，只要存在越权采集、隐私传播、自动上传、隐藏通信、恶意控制、知识产权争议或其他无法合理排除的风险，就不得合并或发布。有疑义的功能应先暂停，完成合规评估或取得平台书面确认后再决定。

项目遵循适用法律法规、《魔兽世界》国服运营规则、网易 DD 平台审核要求和相关活动的最新公开规则。规则发生变化时，项目应重新评估受影响功能，并在必要时回滚、禁用或下架。

## 3. 项目身份与权利边界

- 项目名称为 **BGNext**，定位为 BGLite 纯净版基础上的社区共创维护项目。
- BGLite、《魔兽世界》名称、商标、代码、图片、声音及其他既有内容的权利归各自权利人所有。
- 仓库不会把上游代码错误声明为本项目原创，也不会在未取得充分权利的情况下擅自套用 MIT、GPL 等开源许可证。
- 第三方库保留其原有版权声明和许可证。
- 贡献者必须保证其提交内容为本人原创或已获得合法、可验证的使用授权。
- 项目的独立贡献、仓库治理文件和未来新增素材，需要在权利条件明确后再确定统一许可方案。

## 4. 社区共创机制

项目欢迎插件作者、玩家、测试者、翻译者、设计师、文档贡献者和合规审查者参与。代码、错误报告、兼容性测试、翻译、文字校对、设计和安全建议均属于有效贡献形式。

工作流程如下：

1. 新功能和重要改动原则上先通过 GitHub Issue 描述需求、使用场景、数据行为和潜在风险。
2. 实现通过独立分支和 Pull Request 提交。
3. Pull Request 必须说明改动范围、测试结果、隐私影响、通信行为、素材来源和兼容性影响。
4. 至少完成维护审查、合规检查和必要测试后方可合并。
5. 新版本通过网易 DD 或适用发布平台审核后方可作为正式版本发布。

贡献者不需要先加入维护团队。小型修复、复现报告、文档和测试贡献应得到与其实际价值相符的认可。

## 5. 贡献者致谢

仓库在 `docs/community/CONTRIBUTORS.md` 按贡献类型记录贡献者，不按贡献金额或个人影响力排序。可记录的类别包括：

- 代码与架构；
- 测试与问题复现；
- 翻译与文档；
- 视觉与交互；
- 安全、隐私与合规审查；
- 社区维护。

每个 Release 的更新日志列出相关 Pull Request 和贡献者。列入感谢名单只代表存在可核验的实际贡献，不代表该贡献者为整个项目背书或承担其他模块的责任。不得出售署名，不得根据赞助金额调整名单顺序或显著程度。

## 6. 数据与隐私边界

- 插件产生的数据默认仅保存在玩家本地。
- 禁止未经玩家许可收集、保存或传播账号、角色、设备、聊天、战斗、交易等信息。
- 禁止在插件加载、角色登录、进入副本或其他游戏行为发生时自动触发外部上传或同步。
- 禁止隐藏采集、隐藏传输、遥测、跟踪标识或未披露的外部通信。
- 导出或传输必须由用户主动、手动触发。
- 用户触发前必须明确说明数据内容、用途、接收方和可能风险。
- 不收集完成核心功能所不需要的数据；可用匿名或聚合数据完成时不得使用可识别数据。

## 7. 禁止功能与内容

项目不接受以下内容：

- 后门、远程控制、外部可执行程序或影响游戏稳定性的恶意逻辑；
- 博彩、现金交易导流、刷量、买量、诱导重复下载；
- 强制分享、强制关注、强制好评或虚假宣传；
- 绕过玩家明确操作、在后台代表玩家完成敏感行为的逻辑；
- 未授权的代码、UI、图片、字体、声音或文案；
- 规避平台审核、隐藏真实数据行为或故意误导审查人员的实现；
- 其他违反适用法律、游戏规则、平台规则或损害玩家权益的功能。

## 8. 慈善与财务透明

与 BGNext 相关的全部活动奖金、赞助及其他项目收入均用于慈善捐赠，不作为维护者或贡献者的个人收益。

如依法产生必须缴纳或代扣代缴的税费，应单独记录并披露；扣除依法必须承担的税费后，剩余资金全部捐赠给具备合法资质、信息可核验的慈善组织。

项目通过 `docs/policies/CHARITY.md` 公开记录收入来源、金额、必要税费、受赠机构、捐赠日期和凭证链接。涉及身份证件、银行账号、地址等个人敏感信息的凭证必须脱敏后公开。不得以捐赠或赞助金额换取代码合并、功能优先级、维护权限、署名排序或审核豁免。

## 9. 文档与 GitHub 配置结构

正式实施阶段新增以下非运行时文件：

- `README.md`：项目入口、缘起、目标、当前基线、安装、共创方式、合规原则、慈善承诺和免责声明。
- `SECURITY.md`：支持版本、安全问题私下报告方式、响应流程和披露规则。
- `docs/policies/PRIVACY.md`：数据清单、处理原则、导出与传输规则、用户控制和变更通知。
- `CONTRIBUTING.md`：Issue、分支、提交、Pull Request、测试、版权和审查要求。
- `CODE_OF_CONDUCT.md`：社区行为准则及处理机制。
- `COPYRIGHT.md`：上游、第三方和新增贡献的权利说明；不擅自授予未获授权的许可证。
- `CHANGELOG.md`：版本历史；首条只记录 BGLite 2.4.0 原版基线导入。
- `docs/community/CONTRIBUTORS.md`：按贡献类型整理的感谢名单及收录规则。
- `.github/SUPPORT.md`：使用问题、错误报告、安全问题的分流方式。
- `docs/policies/PROJECT_CHARTER.md`：治理结构、维护者职责、决策和发布规则。
- `docs/policies/COMPLIANCE.md`：允许、需评估和禁止功能的边界与评审清单。
- `docs/policies/CHARITY.md`：慈善政策、公开账目格式和凭证规则。
- `docs/baseline/BGLite-2.4.0.sha256`：188 个上游文件的 SHA-256 清单。
- `.github/ISSUE_TEMPLATE/`：错误报告和功能建议表单。
- `.github/pull_request_template.md`：测试、隐私、通信、素材和兼容性检查项。
- `.github/workflows/baseline-integrity.yml`：验证原版基线文件未被未说明地修改。

仓库文档以中文为主。必要的项目摘要、Issue 字段和关键合规声明可同时提供简洁英文，便于第三方审查与国际贡献者理解。

## 10. 发布与变更管理

- `main` 只接收经过审查并通过验证的变更。
- 功能开发使用独立分支，不直接在正式 Release 页面编辑未验证产物。
- Release 包只包含插件运行所需文件，不把仓库治理文档打入 WoW 插件目录。
- Release 必须包含版本号、支持的游戏版本、变更说明、校验值、已知问题和贡献者致谢。
- 发布前验证原版基线差异、Lua 加载、关键拍卖流程、跨版本兼容、隐私行为和数据传输行为。
- 未通过平台审核的新版本不得替换已发布的稳定版本。

## 11. 验收标准

完成专业化文档后必须满足：

1. 188 个 BGLite 2.4.0 基线文件与原始来源逐文件 SHA-256 一致。
2. 仓库没有未经授权的许可证声明或官方背书表述。
3. README 能让新访客快速理解项目是什么、为什么存在、如何参与以及哪些功能永远不会接受。
4. Issue 和 Pull Request 模板强制披露数据、通信、版权和测试信息。
5. SECURITY、PRIVACY、COMPLIANCE 三份文档不存在相互冲突的规则。
6. 慈善政策明确覆盖全部项目收入，同时对依法必须承担的税费和隐私脱敏作出说明。
7. 文档提交不包含插件运行时代码改动。
