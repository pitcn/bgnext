# Feature Catalog, Basic Mode, and In-Game Guide Design

## Status

Approved by the maintainer on 2026-09-04 with authority to use the recommended design without further review checkpoints.

## Problem

BGNext has accumulated useful enhancements on top of BGLite, but their settings, entry points, commands, shortcuts, and help text are maintained in different places. Players who prefer a simpler experience cannot disable coherent groups of enhancements, and maintainers can add a public action without updating the in-game guide.

## Goals

- Give players a reversible “basic mode” while retaining required compatibility, safety, migration, and privacy behavior.
- Allow individual optional features to be enabled after choosing basic mode.
- Drive settings and the in-game guide from one declarative catalog.
- Preserve every existing user's enabled experience on upgrade.
- Make missing documentation for public commands and shortcuts detectable by tests.

## Non-goals

- This work does not reproduce official BGLite by swapping code paths or loading a second addon.
- It does not delete feature data, change auction protocols, weaken send-time gates, or add communication.
- It does not redesign the pending-auction window; that remains Issue #80.
- It does not add Mists character tracking; that remains Issue #63.

## Architecture

### Feature catalog

Add a small BGNext-owned catalog module. Each entry has a stable ID, group, localized name/summary keys, availability predicate by client family, optional dependencies, public entry/command/interaction metadata, and one of two policies:

- `required`: always active and shown as such. This includes compatibility behavior, auction pre-send gates, trade-capture correctness, data lifecycle/migrations, and storage/privacy controls.
- `optional`: controlled through `BiaoGe.BGNext.settings.features[id]`.

The catalog is metadata only. It does not hold player data or call runtime modules.

### Settings model

Add a settings service with the public operations `isEnabled`, `setEnabled`, `applyMode`, and `mode`. It sanitizes only known optional IDs and ignores unknown persisted keys.

Absence of a feature value means enabled. This makes both new installations and upgrades from every existing BGNext version retain the current complete experience without a bulk migration write. Explicit booleans are persisted only after player action.

`applyMode("basic")` writes `false` for the catalog's basic-mode optional set. `applyMode("full")` writes `true` for all available optional entries. If the user changes one item so the saved values no longer match either preset, `mode` returns `custom`.

Dependencies affect effective availability without overwriting a dependent feature's saved preference. Re-enabling the parent restores the dependent feature.

### Runtime integration

Each optional runtime has one named catalog ID. Its visible entry, command handler, collection/event work, and refresh work check the settings service at their existing boundary. Required safety gates remain active even when the feature they protect is hidden.

The first implementation covers BGNext-owned enhancements with stable, testable boundaries:

- wishlist and wishlist reminders;
- auction price presets;
- pending auction queue, including the loot-window entry;
- current-settlement records/checklist/return markers;
- own-character overview;
- equipment filtering;
- optional UI appearance enhancements;
- trade announcements.

Where a baseline BGLite callback cannot be safely unregistered, the BGNext wrapper returns immediately while disabled. No new polling or repeating timer is introduced.

### Feature management UI

Add a “功能管理 / Feature Management” options tab. The top row offers Full and Basic presets and displays the derived state: Full, Basic, or Custom. Below it, optional and required features are grouped into personal tools, auction tools, settlement tools, and interface enhancements.

Optional rows use checkboxes. Required rows have no checkbox and display “始终启用 / Always enabled”. Unavailable client-specific entries are omitted. Toggling a feature never deletes its SavedVariables.

### In-game guide

Replace the oversized hover-only manual with a closable, scrollable BGNext guide window opened from the existing top “说明书” entry. The first section is Quick Start; subsequent sections are generated by catalog group and include applicable descriptions, commands, mouse/keyboard interactions, contextual permissions, and destructive-action warnings.

Only current-client entries are shown. Required protections and the distinction between basic mode and installing official BGLite are explained explicitly. Disabled features remain documented and identify the Feature Management page used to enable them.

The catalog registers public slash commands and shortcut descriptions. Tests compare the known public BGNext command/interaction inventory with catalog declarations. Internal/debug-only actions are not presented to players.

## Data and privacy

The only new persisted values are booleans under `BiaoGe.BGNext.settings.features[featureId]`. They record feature preferences only. No history is stored, no existing feature data is removed, and nothing is transmitted. The data inventory must document the field, retention, and reset control.

## Localization and compatibility

All player-facing strings have Simplified Chinese, Traditional Chinese, and English fallback entries. The guide uses a scroll view and measured controls so English text does not determine a fixed Chinese-only width. Client applicability is declared in the catalog and automatically tested; unverified support is not advertised.

## Failure behavior

- Unknown or malformed saved feature values fall back to enabled and are not executed as IDs.
- Required features ignore disable attempts.
- A disabled public slash command prints a local explanation and does not silently fail.
- Missing dependencies make a feature effectively disabled without changing its saved preference.
- A missing optional UI dependency hides that control instead of throwing during load.

## Testing

Use vertical RED→GREEN slices through public module interfaces and UI harnesses:

1. catalog validation and stable command/interaction inventory;
2. default/upgrade behavior and unknown-value sanitation;
3. Full, Basic, Custom, dependency restoration, and reload persistence;
4. feature-management tab behavior and required-feature presentation;
5. guide entry, close/scroll behavior, current-client filtering, and three-language fallback;
6. representative runtime gates proving disabled entries and event work stop without deleting data;
7. complete Lua suite, baseline manifest, Lua 5.1 parse, diff-check, and high-risk agent verification.

Real-client layout and every optional module's user flow remain explicit game-validation items.
